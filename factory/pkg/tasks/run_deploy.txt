1. Execute deploy.sh. If a step fails, fix the script — not just the
   moment — so the next run is deterministic.

   THE ATTEMPT BUDGET IS 3. Cloud attempts cost real money — every
   create/delete cycle spins up and destroys real resources. Rules:
   - Before re-running, diagnose with READ-ONLY commands (describe,
     get-iam-policy, list) until you can name the failure's cause.
     Never re-run the script just to see the error again.
   - If the same failure signature appears twice, STOP — it will not
     fix itself on the third try.
   - Repairs must respect ownership: never fix a failure by adopting
     infrastructure this run did not create (an existing cluster
     belongs to another run). Resources you create are named
     ${RESOURCE_PREFIX}[-suffix], and labeled
     repo-agent-instance=${RESOURCE_PREFIX} where the service
     supports labels — the NAME is the ownership guarantee, the
     label is a bonus for auditing.
   - A permission, quota, or billing failure is BLOCKED, not a bug you
     can fix: confirm it read-only (e.g. testIamPermissions, a denied
     describe), then STOP immediately. Do not keep creating and
     deleting resources around a wall only the owner can remove.

2. When you stop for any reason, leave the world accounted for: tear
   down partial resources THIS run created (or, if they are the
   deployment, leave them and say so) — never leave unrecorded
   half-built infrastructure.

3. If a fix requires changing the REPOSITORY's own source, capture it
   as a patch file in this run's directory (git diff >
   patches/<name>.patch) and have deploy.sh apply it before building.
   A source edit that lives only in this sandbox's working tree makes
   the deployment unreproducible: the next run builds unpatched code
   and fails differently. If the change is right for everyone, say so
   in the receipt — it belongs in a PR, not in a deployment.

4. RECONCILE runbook.md — once, at the end, after your final attempt.
   Bring the procedure back in line with the scripts as they now
   stand: a step you had to reorder, a flag you had to add, a step
   that turned out to be unnecessary. Keep the prose explaining WHY,
   because that is what the next reader needs — "wait for the
   nodepool before granting WI; the binding fails against a cluster
   still provisioning" is worth more than the flag alone.

   Do this whether the deploy succeeded or failed. runbook.md is not
   a claim that the procedure works — the receipt's verdict says
   that. runbook.md is the readable form of these scripts, and if the
   scripts changed and it did not, the next revision starts from a
   document that no longer describes them.

   Do not rewrite it wholesale, and do not restate the attempt log
   there. Change the steps that changed.

5. Write the receipt to
   docs-exploration/agent-runs/{{.Name}}/receipt-<UTC yyyymmdd-hhmm>.md:

   - "## Procedure amended" — one line per change you made to
     runbook.md, each naming WHY: the failure or constraint that

     Headlines only; the detail is in the file and the diff is one

   - the Verify evidence when it succeeded.
   - what is left RUNNING and where — the teardown contract.
   - cost-relevant resources created.
   - a BLOCKED receipt must carry "## Needs from owner" with the

6. Only when execution succeeded: verify per runbook.md's Verify

Do not commit or push — the task harness commits and pushes when you
