1. Execute deploy.sh. If a step fails, fix the script — not just the
   moment — so the next run is deterministic; note what changed in one
   line at the top of the script.

   THE ATTEMPT BUDGET IS 3. Cloud attempts cost real money — every
   create/delete cycle spins up and destroys real resources. Rules:
   - Before re-running, diagnose with READ-ONLY commands (describe,
     get-iam-policy, list) until you can name the failure's cause.
     Never re-run the script just to see the error again.
   - If the same failure signature appears twice, STOP — it will not
     fix itself on the third try.
   - Repairs must respect ownership: never fix a failure by adopting
     infrastructure this instance did not create (an existing cluster
     belongs to another instance). Resources you create are named
     ${RESOURCE_PREFIX}[-suffix], and labeled
     repo-agent-instance=${RESOURCE_PREFIX} where the service
     supports labels — the NAME is the ownership guarantee, the
     label is a bonus for auditing.
   - A permission, quota, or billing failure is BLOCKED, not a bug you
     can fix: confirm it read-only (e.g. testIamPermissions, a denied
     describe), then STOP immediately. Do not keep creating and
     deleting resources around a wall only the owner can remove.
2. When you stop for any reason, leave the world accounted for: tear
   down partial resources THIS run created (or, if they are the
   deployment, leave them and say so) — never leave unrecorded
   half-built infrastructure.
3. Document what you learned where the next actor needs it:
   - If a fix requires changing the REPOSITORY's own source, capture
     it as a patch file in your instance directory (git diff >
     patches/<name>.patch) and have deploy.sh apply it before
     building. A source edit that lives only in this sandbox's
     working tree makes the deployment unreproducible: the next run
     builds unpatched code and fails differently. If the change is
     right for everyone, say so in the receipt — it belongs in a PR,
     not in a deployment.
   - THE RUNBOOK IS READ-ONLY TO YOU. It is the owner's document,
     reviewed at the plan gate and shared by every instance; a deploy
     run must never edit it. Write only inside your instance
     directory.
   - Instead, end the receipt with "Recommended runbook changes": the
     requirements this run discovered (exact IAM roles, APIs, quotas)
     and — if a repair changed the APPROACH rather than a detail
     (published charts where the runbook builds from source, a
     different tool or service) — the replacement text for the Steps
     it affects, written so the owner can apply it verbatim. Errors
     must make the runbook smarter, but through the owner's Update
     Runbook click, not behind their back.
   - Write the receipt to
     docs-exploration/runbook-deployments/{{.Instance}}/receipt-<UTC yyyymmdd-hhmm>.md:
     verdict on the first line — VERIFIED / DEPLOYED-UNVERIFIED /
     FAILED / BLOCKED — then, if this run did anything the runbook
     does not say, a single line immediately under it:
     "⚠ Deviated from the runbook: <what, in one clause>" (and
     nothing there when it followed the runbook). A reader meets the
     causality before the detail: what happened, then why it differs
     from the recipe they reviewed. Then an attempt log (attempt N: what failed,
     the evidence, what you changed), the Verify evidence when it
     succeeded, what is left RUNNING and where (the teardown
     contract), and cost-relevant resources created. Close with
     "Deviations from the runbook": one entry per difference, each
     naming WHY — the failure or constraint that forced it and the
     attempt it came from ("no local docker daemon → Cloud Build";
     "attempt 2: source build hit a ClusterTrustBundle
     incompatibility → published charts"). A deviation without a
     reason reads as a whim and leaves the owner unable to judge
     whether the runbook or the deployment is wrong. A BLOCKED receipt
     must carry a "Needs from owner" section with the EXACT commands
     that unblock it (gcloud grant / enable-api / quota request).
4. Only when execution succeeded: verify per the runbook's Verify
   section — probe the endpoints, run the health commands, read the
   output. Judgment matters here; a clean exit code is not
   verification.
