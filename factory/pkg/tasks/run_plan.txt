Write the files in this order. The order is the point: the procedure
is the thinking and the scripts are a transcription of it. Writing
shell first turns runbook.md into a summary of the scripts, it drifts
on the next revision, and the owner loses the thing they review.

1. runbook.md — the procedure, in prose, for a human to read and
   approve. Follow the section structure in docs-exploration/SKILL.md
   in this checkout: What this needs, Preconditions, Steps, Verify,
   Teardown. Number the steps. Under each step, put the commands it
   runs in a fenced code block. Say WHY where a choice is not
   obvious: a reader should be able to tell a deliberate decision
   from an accident.

   Derive the real path from the repository's own tooling: the
   Makefile, scripts/, CI workflows (.github/workflows is the ground
   truth for what actually builds and tests), helm charts, kustomize
   bases, container files. Do not invent commands — every step must
   trace to something the repo ships.

   Open What this needs by answering one question plainly: can this
   run in the pod (binaries, tests, envtest, a single-process
   server), or does it need real infrastructure? Node-level reality
   forces the latter: CSI drivers, device plugins, privileged
   DaemonSets, kubelet sockets, host mounts. Say which component
   forces it.

   Keep runbook.md ACCOUNT-AGNOSTIC. Project ids, regions and cluster
   names are parameters and belong in params.env; in the procedure
   they are variables the reader sets. A procedure that names a
   project works for exactly one person and then silently misleads
   the next.

   If runbook.md ALREADY EXISTS, revise it rather than replacing it.
   It may carry corrections learned from a real deployment, and
   regenerating from the original intent throws those away. Change
   what the new instruction asks for and leave the rest standing.

2. params.env — every parameter as a shell variable (PROJECT, REGION,
   CLUSTER, names…), one place to see what makes this run THIS run.
   LITERAL VALUES ONLY: resolve the environment NOW (the owner's
   intent wins, then GOOGLE_CLOUD_PROJECT, CLOUDSDK_COMPUTE_REGION,
   RUN_RESOURCE_PREFIX) and write what you resolved —
   PROJECT="my-proj"  # from Settings — never ${VAR:-fallback}
   indirection. The owner reviews params.env at the plan gate; a
   value that resolves at execution time defeats the review, and a
   stale fallback misleads it.

   It MUST define RESOURCE_PREFIX as the literal value of
   RUN_RESOURCE_PREFIX (already unique across every board sharing the
   project). Every cloud resource this run creates is named
   ${RESOURCE_PREFIX}[-suffix] and labeled
   repo-agent-instance=${RESOURCE_PREFIX} where the service supports
   labels.

3. deploy.sh — deterministic bash, set -euo pipefail, sources
   params.env. Every command must be one that appears in a fenced
   block in runbook.md: the script may not do anything the procedure
   does not describe. No secrets, ever — credentials come from the
   environment (Workload Identity).

4. teardown.sh — runbook.md's Teardown section, same rules.

5. receipt-<UTC yyyymmdd-hhmm>.md — PLANNED on the first line, then
   what this run will create (names, from params.env), roughly what
   it will cost, the feasibility state (✓/✗ per step), and anything
   the owner should read before approving.

   If an earlier receipt in this directory reported resources left
   RUNNING, carry them forward under "## Currently deployed" —
   verbatim, with the receipt they came from. Planning does not
   remove infrastructure, and this receipt is the newest thing
   anyone reads: drop that list and a live cluster becomes invisible,
   nobody offers to tear it down, and it bills until somebody
   notices. Say plainly that this plan supersedes the deployed state
   and has not been applied.

OWNERSHIP: this run owns everything it touches. Never write steps that
adopt infrastructure this run did not create — a healthy existing
cluster in the project is NOT permission to use it; another run owns
it, and your deploy or teardown would land on someone else's
deployment. Using pre-existing infrastructure requires the owner
naming it explicitly above (then pin it in params.env). No intent
given means create your own, never borrow.

VERIFY FEASIBILITY before you claim a step works. You are running
under the SAME identity and in the same kind of environment this run
will execute in, so check, don't assume:
  - Permissions: enumerate the IAM permissions each step needs (what
    does the tool CREATE and BIND? kops on GCE, for example, creates
    service accounts, attaches them to instances —
    iam.serviceAccounts.actAs — and binds project roles —
    resourcemanager.projects.setIamPolicy). Probe with read-only
    calls: projects.testIamPermissions, a get-iam-policy, a dry-run
    where the tool offers one.
  - Tools: verify the binaries the steps call actually exist here (a
    missing docker daemon means Cloud Build, not a doomed step).
    Verification means --version, --help and dry-runs.

Write the results into What this needs as a checklist: ✓
granted/present, ✗ MISSING — each missing item with the exact command
that grants or installs it. Never write steps around a missing
permission; name it instead. A plan whose requirements are not met is
a pre-run checklist for the owner, not a discovery the deploy makes
at VM prices.

IF THE PARAMETERS CANNOT BE RESOLVED — no GCP project configured, a
target the owner has not chosen, a required value nowhere to be found
— stop after runbook.md. Write no params.env and no scripts, and make
the receipt BLOCKED instead of PLANNED, with a "## Needs from owner"
section naming exactly what is missing and the command or setting
that supplies it. A procedure the owner can read and act on is worth
far more than scripts built on invented values.

Do NOT execute anything. Do NOT create cloud resources. Do NOT build
or run tests — not even push-disabled builds: HEAD moves, so the
deploy's build is the only one that certifies anything, and the plan
must stay fast enough to review while the owner is still looking.

Do not commit or push — the task harness commits this directory when
you are done. Finish with one paragraph: this run's parameters and
anything you had to decide.
