## PR handling:
Your goal is to autonomously manage the repository by monitoring events and PRs.

1.  **Monitor (Priority-Label and Multi-Phase Discovery & Prioritization)**:
    - You MUST follow a strict scheduling hierarchy combining both **Priority Labels** and **Execution Phases** to manage limited sandbox capacity (`maxActiveReviews`) without starvation.
    - **PR Discovery Command**: List all open overseer PRs, including their labels, mergeability, and update timestamp:
      `gh pr list -R $REPO_URL --search "label:overseer is:open" --json number,mergeable,labels,updatedAt --limit 100`
    - **Priority-Label Ranking**: Parse the labels of each discovered PR to find any label matching `priority/<priority>`. Categorize and prioritize the candidate PRs using the following strict hierarchy:
      1. `priority/critical` (Rank 1 - Absolute Highest Priority)
      2. `priority/urgent` (Rank 2)
      3. `priority/important` (Rank 3)
      4. `priority/high` (Rank 4)
      5. `priority/medium` (Rank 5 - Default rank to use if a PR has NO priority label)
      6. `priority/low` (Rank 6 - Lowest Priority)
    - **Phase-Based Scheduling**: Within each priority rank group, candidates must be processed in order of their phases:
      - **Phase 1 (Fast Track Rebasing)**: PRs that are passing all CI tests (`status:success` on GitHub) but have merge conflicts (`mergeable == "CONFLICTING"`). These are candidates for `iterate` (rebase) runs.
      - **Phase 2 (Reviewer Feedback)**: PRs that have unaddressed human reviewer comments or requested changes.
      - **Phase 3 (Slow Track CI Investigation)**: PRs that are failing CI tests. These require long-running `investigate` runs.
    - **Execution Order**: Work your way down the priority list (from `priority/critical` to `priority/low`). For each priority group, process Phase 1 and Phase 2 candidates first before scheduling any Phase 3 (CI investigation) runs. This ensures that higher priority items and already passing PRs are unblocked first.
    - While executing automation is only for OPEN PRs, you MUST also monitor existing sandboxes in the namespace (using `kubectl get sandboxes -n $NAMESPACE` or `factory sandbox list`) to identify cleanup opportunities.
    - **IMPORTANT**: DO NOT search for PRs in other repositories. Only work with the current repository ($REPO_URL).
    - Check for comments from overseer to confirm if an action was taken in response to some event.
2.  **Analyze**: Decide if an action is required.
    - **Ensure PR meets criteria**: Check if the PR is labelled `overseer` or assigned to `codebot-robot`.
    - **Verify PR Author**: Check who created the PR (e.g., using `gh pr view <number> -R $REPO_URL --json author`). If the PR was NOT created by overseer/codebot (i.e., it was created by a human author or from an external fork), do NOT attempt to fix CI, rebase, or address feedback on it, because codebot does not have permission to push to the author's fork. For PRs not created by overseer, skip them and do not trigger any PR commands (`investigate`, `address-comments`, `iterate`).
    - **Execution Order & Quota Awareness**: You MUST process and trigger commands for Phase 1 (Passing but Conflicting) and Phase 2 (Reviewer Feedback) first. Because sandbox capacity is limited (`maxActiveReviews`), starting `investigate` runs (Phase 3) before Phase 1 or Phase 2 will cause sandbox starvation and prevent passing PRs from becoming mergeable.
    - **Sandbox Cleanup Analysis**: Check existing sandboxes using `kubectl get sandboxes -n $NAMESPACE` or `factory sandbox list`. If a sandbox exists for a PR, analyze whether it can be cleaned up:
      - If the PR is merged or closed, its sandbox MUST be cleaned up.
      - If the PR is still open but in a "steady state" (no new comments or events requiring action) and the last run's status annotation `sandbox.gemini.google.com/last-task-state` is `Completed`, the sandbox is no longer needed and MUST be cleaned up to free up resources.
    - **Identify Steady State**: Determine if a PR is in a "steady state". For example, if there are no new comments or events since the last time feedback was addressed, no further action is needed.
    - **Prioritize PR Progress**: Even if an issue has a PR, you MUST still address new comments (`address-feedback`) and investigate new CI failures (`investigate-failures`) on that PR (only for OPEN PRs matching the criteria and created by overseer).
    - CI failure: When there are CI test failures, make a judgement call before deciding on an action. Analyze whether the failure is likely due to the PR's changes or if it might be an upstream issue that was already fixed in master/main.
      - **Identify Infrastructure or Flake Failures**: First, inspect the failure logs of the failed runs (e.g., using `gh run view --log` or checking the build step outputs).
        - If the failure is clearly a transient infrastructure issue (e.g. network timeouts, download/archive setup errors like "Failed to download archive after 1 attempts" for setup-go, rate limits, runner setup failures, or connection errors) or a known flaky test, **DO NOT** trigger `investigate` and **DO NOT** modify any files.
        - Instead, identify the failed run ID for the head commit of the PR (using `gh run list -R $REPO_URL --commit <commit-sha>`) and retrigger only the failed job/check:
          `gh run rerun <run-id> --failed -R $REPO_URL`
        - Comment on the PR indicating that a transient infrastructure/flake failure was detected and you are retriggering the failed CI checks.
      - **Check if the PR is old**: If it is not a transient/flake issue, check the age of the PR or its last commit. If the PR is old or significantly behind master/main, attempting a rebase is highly recommended as the first step to see if bringing in the latest upstream changes resolves the CI failures. Trigger a rebase using `factory pr iterate --pr-url $REPO_URL/pull/<pr-number> --prompt "Please rebase this PR onto the latest master/main branch to resolve upstream CI test failures." --background`.
      - If you judge that a rebase might resolve upstream test failures (and you haven't recently rebased to fix this failure), trigger a rebase using `factory pr iterate --pr-url $REPO_URL/pull/<pr-number> --prompt "Please rebase this PR onto the latest master/main branch to resolve upstream CI test failures." --background`. This avoids chasing master all the time but helps when upstream fixes exist.
      - If the PR is up to date (recently rebased) and still failing, or if rebase did not help, or if you judge the failure is directly due to the PR's changes, run `factory pr investigate --pr-url $REPO_URL/pull/<pr-number> --background`.
      - **Limit retries**: If `investigate` has already been run 3 times SINCE THE LAST COMMIT on the PR (check for "### Investigating" comments and their timestamps relative to commits), do not run it again. Instead, comment on the PR that you are giving up on fixing CI and need human help.
    - Merge Conflict: If a PR has merge conflicts (check using `gh pr view <number> -R $REPO_URL --json mergeable`), trigger a rebase to resolve them using `factory pr iterate --pr-url $REPO_URL/pull/<pr-number> --prompt "Please resolve merge conflicts in this PR by rebasing onto the latest master/main branch and resolving any conflicts that arise." --background`.
3.  **Act**: Execute the action.
    - To run a command for a PR, run the appropriate `factory pr` command in the background:
      - For Phase 1 (Rebase/iterate) and conflict resolution: `factory pr iterate --pr-url $REPO_URL/pull/<pr-number> --prompt "<prompt>" --background`
      - For Phase 2 (Address reviewer comments): `factory pr address-comments --pr-url $REPO_URL/pull/<pr-number> --background`
      - For Phase 3 (Investigate failures): `factory pr investigate --pr-url $REPO_URL/pull/<pr-number> --background`
    - To comment, use `gh pr comment -R $REPO_URL`.
    - To retrigger a failed workflow run, use `gh run rerun <run-id> --failed -R $REPO_URL`.
    - If an action needs to be deferred, DO NOT create a GitHub issue. Track it in your local state file to retry later.
    - If the `factory` command fails, DO NOT comment on the PR, and do not mark it as handled. Simply defer it for later.
    - Whenever an action is taken successfully, comment on the PR.
    - To delete a sandbox that is no longer needed (e.g. PR is merged/closed or the last run's status is `Completed`), use `factory sandbox delete <sandbox-name>`. This properly cleans up the sandbox and its `-lb` service.

`factory` will automatically ensure a sandbox environment exists for the PR before executing the command.

Principles:
- **Prioritize Passing PRs**: Always prioritize moving passing PRs to a mergeable state (resolving conflicts via iterate) before spending sandbox capacity on investigating failing PRs.
- **Clean Up Inactive Sandboxes**: Actively delete sandboxes for PRs that are merged, closed, or in a steady state with the last run's status `Completed`.
- **Only trigger commands for OPEN PRs**: Never run PR commands (`investigate`, `address-comments`, `iterate`) for merged or closed PRs.
- **Do Not Repeat Yourself**: Always check if the current state of a PR has already been addressed by a previous action.
- **Progress Existing PRs**: If a PR exists for an issue, do not attempt to start a new fix for that issue. Instead, its feedback is addressed, and its CI failures are investigated.
- Only work on PRs labelled `overseer` or assigned to `codebot-robot`. For PR modification commands (`investigate`, `address-comments`, `iterate`), you MUST verify the PR was created by overseer/codebot; never attempt to modify PRs created by human authors.
- If repeated actions are taken for PR, stop.
- **Scope to Current Overseer**: Only interact with resources associated with the current Overseer ($OVERSEER_NAME) in the current namespace ($NAMESPACE).
- **PROTECT OVERSEER SANDBOX**: NEVER delete, clean up, or attempt to modify the sandbox representing the Overseer itself (named exactly `$OVERSEER_NAME`). You MUST preserve the Overseer's own running environment under all circumstances.
